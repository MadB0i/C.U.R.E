# STAGE UI-02 — AI Agent Radar & Flight Recorder Acceptance

**Branch:** `feat/cure-operator-storage-defense` · **Baseline:** `49e51d6` (Stage UI-01A)
**Scope:** Agents page only (radar, agent inventory, Flight Recorder, Windows Change Radar, case file) plus agent-specific state sync.
**Binary used for all native checks:** `gui/src-tauri/target/release/cure-gui.exe` — real Tauri + WebView2 + Rust backend, no mocks.

## Root causes of the bugs found

1. **Fresh launch presented detections as a current scan.** `agent-radar.js`
   called `refreshRadar(true)` at module load **and** re-enumerated the
   whole process table on a 3-second timer whenever the page was open. A
   fresh launch therefore showed a live-looking agent list that was never
   requested, and the app burned CPU on process enumeration + per-process
   Authenticode verification every 3 s. Fix: the page now starts in an
   explicit idle state (`Not scanned this session`), the process table is
   read **only** when the operator clicks `Scan Agents` / `Refresh`, and
   the timer only polls the in-process recorder state (`flight_status`,
   cheap, local) plus the real duration readout.
2. **Navigation to the page triggered a hidden scan.** The shell's
   `navTo("view-agents")` called `CureAgentRadar.refresh()`, which
   enumerated processes. `refresh()` now refreshes recorder state only;
   detection is strictly operator-initiated.
3. **Stale radar responses could resurrect a stopped recording.** The
   post-start/post-stop refresh snapshots raced the lifecycle change: a
   response captured while recording could re-apply an active session
   after `flight_stop`. Fix: monotonic `scanSeq` token (stale responses
   are discarded), `renderRadar` only ever *introduces* a session the
   backend still reports as active, and a queued re-scan runs after the
   in-flight one so the final snapshot reflects the newest lifecycle.
4. **A stop click during the start's busy window was silently dropped.**
   Clicking `Stop and review` while `flight_start` was still running
   returned without effect. Fix: the stop is queued and honoured as soon
   as the session exists (a double click never fires a second stop).
5. **Mock drift.** The labelled mock's `agent_radar` payload lacked
   `model_server_count`, process memory, and `operator_agent_sessions`
   carried no `recovery` data and mismatched PIDs — the dev/demo shell
   exercised a shape the real backend never produced. The mock now mirrors
   the real DTOs.

## State lifecycle verification

- **Fresh launch:** radar `idle`, center `— / not scanned`, zero blips,
  `Not scanned this session` in the header, the readout and the empty
  state; recorder badge `Idle`; nothing has been read.
- **Manual scan:** sweep runs only while the enumeration is in flight,
  buttons show `Scanning…` and are disabled, duplicates impossible
  (`state.scanning` guard + queued refresh); the snapshot replaces the
  previous one and the header shows `Snapshot HH:MM:SS`.
- **Monitoring:** radar phase `monitoring` (sweep) while a recording is
  actually active; stops when the recording stops.
- **Restart:** `recover_last_session()` restores the newest saved session
  as **stopped** reviewable evidence (`recover_interrupted()` labels
  interrupted runs); it is never presented as live. The radar still says
  `Not scanned this session`.

## Unsupported capabilities (stated, not faked)

- Session **recovery/resume** is not offered anywhere: artifacts are
  reported (found / active / recoverable-label from the backend taxonomy /
  unsupported format), and opaque formats are labelled
  "Recovery unsupported". C.U.R.E never opens or modifies agent session
  databases.
- Process exit between scans is only visible in the next manual snapshot;
  there is no background process watcher (and no fabricated live states).
- No CPU% is shown (not measured); memory is shown only when the OS
  returns a working-set value.
- No cancel control for the rescue scan or agent scan: the backend
  exposes no cancellation for these operations.

## Performance / resource notes

- The 3-second full process-table enumeration (with per-process
  Authenticode checks) is gone; idle CPU cost of the page is one cheap
  in-process `flight_status` poll every 3 s while the page is visible.
- The radar sweep is a single CSS rotation on one SVG group, active only
  during scanning/monitoring; `prefers-reduced-motion` disables it and
  the recording pulse.
